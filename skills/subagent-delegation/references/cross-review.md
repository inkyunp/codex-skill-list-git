## 왜 다른 회사 모델인가

"경쟁사 모델이라서 더 엄격하게 본다"는 근거가 아니다. 실제 근거는 하나다.

> 학습 데이터와 사후학습 방식이 달라 **맹점이 덜 겹친다.**

부수적으로 작성 모델의 표현 스타일에 덜 동조하고, 같은 계열이 공유하는 공통 오류를 잡을 가능성이 있다.

반면 알려진 함정이 있다.

- **자기선호 편향** — 모델은 자기 계열 출력이나 자신에게 익숙한 형태를 선호한다.
- **위치 편향** — 같은 두 답변도 제시 순서에 따라 판단이 달라진다.
- **다수결의 실패** — 리뷰어를 늘려 다수결하면 잘못된 비판을 채택하거나 다수 의견에 끌린다. 다양성의 효과는 최종 판정자가 제대로 고를 수 있을 때만 유지된다.

따라서 **토론이 아니라 독립 감사**로 설계한다. 리뷰어끼리 대화시키지 않고, 각자 독립적으로 판정하게 한 뒤 메인이 근거를 비교한다.

## 리뷰 전 자동 검증

**LLM 리뷰는 자동 검증이 끝난 뒤에 돌린다.** 아래에서 잡히는 것을 모델에게 찾게 하는 것은 낭비이고, 리뷰어가 사소한 지적으로 리포트를 채우게 만든다.

```
테스트
타입 검사
린트
빌드
정적 분석
스키마 검증
```

자동 검증이 실패한 상태로 리뷰를 돌리지 않는다. Executor에게 먼저 고치게 한다.

실행 가능한 자동 검증이 없는 산출물(문서·설계안 등)이면 그 사실을 리뷰어에게 알리고, 대신 요구사항 목록을 체크리스트로 넘긴다.

## Reviewer에게 넘길 것과 넘기지 말 것

| 넘긴다 | 넘기지 않는다 |
|---|---|
| 원래 요구사항 | 작성 모델의 이름 |
| 최종 diff 또는 산출물 전문 | 작성자의 자기 평가·자신감 표현 |
| 관련 코드(호출부 포함) | 작성자의 긴 구현 설명 |
| 자동 검증 실행 결과 | 메인의 사전 판단("이 부분이 의심된다") |

마지막 항목이 중요하다. 메인이 의심 지점을 미리 알려주면 리뷰어는 거기만 본다. **의심 지점을 알려주지 않았을 때 리뷰어가 그것을 찾아내는지**가 리뷰의 가치다.

## PASS 판정 기준

```
VERDICT: PASS | FAIL

BLOCKERS:
- [{high|medium}] {path:line} — 문제 / 영향 / 드러나는 조건 / 근거

NON_BLOCKING:
- {path:line} — 개선 의견

VERIFIED:
- 실제로 확인한 코드 경로·테스트·계약

UNCHECKED:
- 확인하지 못한 범위
```

BLOCKERS가 비어 있고 요구사항과 검증이 충족된 경우에만 PASS다.

BLOCKER로 인정되는 것:

```
요구사항 미충족
논리 오류·계약 위반
호출부 누락(시그니처를 바꿨는데 호출 측을 안 고침)
보안·권한·데이터 손실 위험
오류 처리 누락
테스트 부재 또는 부적절
WRITE_PERMISSION 범위 밖 변경
```

BLOCKER가 **아닌** 것: 명명 취향, 코드 스타일, "이렇게 하면 더 우아하다", 기존 코드베이스 전체에 이미 퍼져 있는 패턴에 대한 지적.

리뷰어가 취향 지적만 BLOCKER로 올렸다면 메인이 NON_BLOCKING으로 내리고 PASS 처리한다. **리뷰어의 판정은 근거일 뿐 최종 결정이 아니다.**

## FAIL 이후 절차

```
FAIL → Executor가 BLOCKER만 수정 → Reviewer 재검토 1회 → 종료
```

재검토는 **1회만** 한다. 두 번째도 FAIL이면 Executor를 또 돌리지 않는다. 같은 모델이 같은 문제를 세 번째로 고치지 못하면 문제는 구현이 아니라 요구사항이나 설계에 있다.

이때 선택지는 셋이다.

1. 메인이 직접 개입해 수정한다.
2. 한 단계 상위 모델로 승격해 재구현한다(1회).
3. `ESCALATED`로 종료하고 사용자에게 보고한다.

수정 시 Executor에게는 **BLOCKER 항목만** 전달한다. NON_BLOCKING까지 넘기면 범위가 번진다.

## Arbiter 호출 조건

아래 중 하나일 때만 부른다. 매번 부르지 않는다.

```
Executor가 Reviewer의 BLOCKER를 사실관계로 반박함
두 Reviewer의 결론이 서로 다름
보안·데이터 손실·배포 위험이 크고 근거가 불충분함
Reviewer의 지적이 실제 결함인지 메인이 판정하기 어려움
```

Arbiter에게는 **대립하는 두 주장과 각각의 근거만** 넘긴다. 누가 Executor이고 누가 Reviewer인지는 알릴 필요가 없다. 역할을 알면 "리뷰어가 맞겠지" 쪽으로 기운다.

Arbiter는 절충안을 만들지 않는다. 어느 근거가 사실에 부합하는지만 판정한다.

## 편향 통제 체크리스트

리뷰를 돌리기 전에 확인한다.

```
[ ] 자동 검증을 먼저 돌렸다
[ ] Reviewer가 Executor와 다른 회사 모델이다
[ ] 작성 모델명과 자기 평가를 제거했다
[ ] 메인의 의심 지점을 알려주지 않았다
[ ] Reviewer에게 쓰기 권한을 주지 않았다
[ ] Executor와 Reviewer를 동시에 실행하지 않았다
```

리뷰어를 둘 이상 쓴다면 추가로:

```
[ ] 서로의 리뷰 결과를 보여주지 않았다
[ ] 다수결로 결정하지 않고 메인이 근거를 비교했다
```
