# 파라미터 전체 사양

모든 파라미터는 선택이다. 사용자는 자연어로 말하고, 메인 에이전트가 아래 표로 해석한다. `mode: strategy` 같은 키=값 표기도 그대로 받는다.

## 핵심 파라미터

| 파라미터 | 타입 | 기본값 | 허용 범위 | 설명 |
|---|---|---|---|---|
| `mode` | enum | `idea` | `idea` `strategy` `plan` | 작업 성격. 평가기준 가중치와 산출물 형식을 결정 |
| `depth` | enum | `standard` | `standard` `deep` | 실행 강도 프리셋 |
| `ideators` | int | 3 | 2~4 | 병렬 생성자 수 |
| `judges` | int | 2 | 1~2 | 익명 심사자 수 |
| `challenge_rounds` | int | 0 | 0~1 | 생성자 자기안 보완 라운드 |
| `final_verifier` | bool | `depth`에 따름 | `true` `false` | 타사 모델 최종 검증 여부 |
| `criteria` | list | 기본 7종 | 3~8개 | 평가기준 직접 지정 |
| `constraints` | list | 없음 | 자유 | 예산·기간·인력·기술·규제 등 하드 제약 |
| `context` | path/text | 없음 | 자유 | 참고 자료. 메인이 읽고 브리프에 요약 포함 |
| `output` | path | 없음 | 자유 | 지정 시 보고서를 파일로 저장 |
| `language` | string | 한국어 | 자유 | 산출물 언어 |
| `contrarian` | bool | `false` | `true` `false` | 4번째 생성자로 반론 담당 추가 |

### mode 별 차이

| | `idea` | `strategy` | `plan` |
|---|---|---|---|
| 질문 | 어떤 선택지가 있는가 | 무엇을 선택할 것인가 | 어떻게 실행할 것인가 |
| 가중 기준 | 독창성, 기대효과 | 가정 신뢰도, 차별성 | 실행 가능성, 검증 속도 |
| 후보 형태 | 발산적 아이디어 | 방향 + 근거 | 단계별 실행안 |
| 산출물 | 아이디어 목록 + 추천 | 결정 + 논거 + 대안 | 마일스톤 + 담당 + 검증점 |

`plan` 모드에서 사용자가 이미 방향을 확정했다면 생성자에게 **방향을 고정 제약으로** 주고 실행 경로만 다르게 탐색시킨다.

## 자연어 → 파라미터 해석 규칙

| 사용자 표현 | 해석 |
|---|---|
| "아이디어 뽑아줘", "뭐 할 수 있을까" | `mode: idea` |
| "A랑 B 중에 뭐가 나아", "방향 정해줘" | `mode: strategy` |
| "실행계획", "로드맵", "어떻게 진행할지" | `mode: plan` |
| "제대로", "깊게", "꼼꼼히", "중요한 건이야" | `depth: deep` |
| "빠르게", "가볍게", "대충" | `depth: standard`, `ideators: 2` |
| "많이 뽑아줘", "선택지 넓게" | `ideators: 4` |
| "반대 의견도 들어봐", "비판적으로" | `contrarian: true` |
| "예산 3천만원", "3개월 안에" | `constraints`에 추가 |
| "이 문서 참고해서" | `context`에 경로 |
| "파일로 정리해줘" | `output` 지정 |

`strategy`와 `plan`이 동시에 읽히면 `strategy`를 먼저 돌리고, 승자에 대해 `plan`을 이어서 돌릴지 사용자에게 제안한다. 한 번에 둘 다 하지 않는다.

## depth 프리셋

```yaml
standard:
  ideators: 3
  judges: 2
  challenge_rounds: 0
  final_verifier: false
  # 서브에이전트 호출 5회 내외

deep:
  ideators: 3
  judges: 2
  challenge_rounds: 1
  final_verifier: true
  # 서브에이전트 호출 9회 내외
```

개별 파라미터가 프리셋과 충돌하면 **개별 지정이 이긴다**. `depth: standard`에 `challenge_rounds: 1`을 함께 주면 challenge는 실행된다.

## criteria 지정

기본 7종:

1. 문제 적합성 — 정의된 문제를 실제로 푸는가
2. 기대 효과 — 성공 시 얻는 것의 크기
3. 실행 가능성 — 제약 안에서 가능한가
4. 독창성·차별성 — 기존 대안과 구별되는가
5. 핵심 가정의 신뢰도 — 무엇을 믿어야 성립하는가
6. 실패 위험 — 실패 시 손실과 회복 가능성
7. 빠른 검증 가능성 — 틀렸음을 얼마나 빨리 알 수 있는가

사용자가 `criteria`를 주면 기본값을 **대체**한다(추가가 아니다). 다만 5번과 7번은 심사 품질에 직결되므로, 사용자 지정 목록에 없으면 "추가로 함께 봤다"고 보고서에 명시하고 보조 기준으로 유지한다.

기준은 3개 미만이면 후보 구분이 안 되고, 8개를 넘으면 심사자가 가중치를 잃는다.

## 파라미터 조합 예시

```
# 가장 흔한 형태 — 전부 기본값
$planning-council 신규 사내 교육 프로그램 아이디어 뽑아줘

# 방향 결정 + 제약
$planning-council mode=strategy 3개월 6천만원 안에서
데이터 파이프라인 개편 방향 정해줘

# 깊게 + 반론 담당 추가
$planning-council depth=deep contrarian=true
단일세포 분석 서비스 차별화 전략 검토

# 자료 기반 실행계획 + 파일 저장
$planning-council mode=plan context=./notes/req.md
output=./outputs/plan.md

# 가볍게
$planning-council ideators=2 judges=1 워크숍 주제 후보 좀
```

## 받지 않는 파라미터

아래는 의도적으로 지원하지 않는다.

- **`judges: 3` 이상** — 심사자를 늘려 다수결하지 않는다. 의견이 갈리면 메인이 논거를 비교해 결정한다.
- **`challenge_rounds: 2` 이상** — 라운드를 늘리면 비용은 증가하고 새 정보는 줄며 표현이 수렴한다.
- **`ideators: 5` 이상** — 생성자 수 대비 이익이 둔화되고 동시 실행 슬롯을 넘긴다.
- **자유 토론 모드** — 생성자끼리 서로의 안을 보며 대화하게 하지 않는다. 앵커링으로 다양성이 무너진다.
- **모델 직접 지정** — 사용자가 특정 모델을 요구하면 references/model-routing.md의 가용성 확인을 거친 뒤 반영한다. 카탈로그에 없는 슬러그는 무시하고 대체 모델을 쓴 사실을 고지한다.
