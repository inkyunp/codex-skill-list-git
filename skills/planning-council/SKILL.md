# Planning Council

여러 모델이 **서로의 답을 보지 않고** 기획안을 만든 뒤, 익명 쌍대 비교로 심사하고, 리더가 통합해 최종안을 내는 구조다.

핵심 원칙 세 가지만 기억하면 된다.

1. **처음부터 회의시키지 않는다.** 첫 단계는 반드시 블라인드 병렬 생성이다. 서로의 출력을 일찍 공유하면 앵커링으로 다양성이 무너진다.
2. **점수 대신 쌍대 비교로 심사한다.** 82점/79점 같은 절대점수는 그럴듯할 뿐 실제 차이를 구분하지 못한다.
3. **다양성보다 품질선이 먼저다.** 약한 모델을 "관점이 다르다"는 이유로 핵심 생성·심사에 넣지 않는다.

메인 에이전트가 Brief Architect · Clusterer · Lead Synthesizer를 직접 맡고, 독립성이 중요한 **생성자·심사자·검증자만 서브에이전트로 분리**한다.

## Phase 0 — 파라미터 확정

사용자 요청에서 파라미터를 추출하고, 명시되지 않은 값은 기본값을 쓴다. 되묻지 말고 가정한 값을 아래 한 줄로 고지한 뒤 바로 진행한다.

```
planning-council v1 — mode: {idea|strategy|plan} / depth: {standard|deep} / ideators: N / judges: M / challenge: R / run_id: {YYYY-MM-DD-NNN}
```

전체 파라미터 목록·기본값·해석 규칙은 **references/parameters.md**를 읽는다. 자주 쓰는 것만 요약하면:

| 파라미터 | 기본값 | 의미 |
|---|---|---|
| `mode` | `idea` | `idea` 발상 / `strategy` 방향 결정 / `plan` 실행계획 |
| `depth` | `standard` | `deep`이면 challenge 1회 + 최종 검증자 추가 |
| `ideators` | 3 | 병렬 생성자 수 (2~4) |
| `judges` | 2 | 익명 심사자 수 (1~2) |
| `challenge_rounds` | 0 | 생성자 자기안 보완 라운드 (0~1) |
| `criteria` | 기본 7종 | 평가기준 직접 지정 |
| `constraints` | 없음 | 예산·기간·인력 등 하드 제약 |
| `output` | 대화 내 | 파일 경로 지정 시 저장 |

실행 전 비용을 고지한다. standard는 서브에이전트 호출 5회 내외, deep은 9회 내외다. 단순 기획이면 이 스킬을 호출하지 말고 직접 답한다.

## Phase 1 — Brief Architect (메인 에이전트)

서브에이전트를 띄우기 전에 메인이 직접 브리프를 고정한다. 이 브리프가 모든 생성자에게 **동일하게** 전달된다.

작성 항목:

- 해결할 문제를 한 문장으로
- 성공 상태와 실패 상태
- 하드 제약(예산·기간·인력·기술·규제)과 소프트 선호
- 평가기준 5~7개 (`criteria` 미지정 시 아래 기본값)
- 명시적 범위 밖 항목

기본 평가기준: 문제 적합성 / 기대 효과 / 실행 가능성 / 독창성·차별성 / 핵심 가정의 신뢰도 / 실패 위험 / 빠른 검증 가능성.

`mode`에 따라 기준 가중치를 조정한다. `idea`는 독창성·기대효과, `strategy`는 가정 신뢰도·차별성, `plan`은 실행 가능성·검증 속도에 무게를 둔다.

입력 자료(파일·링크·기존 문서)가 있으면 메인이 먼저 읽고 **요약본을 브리프에 포함**한다. 생성자에게 원문 탐색을 시키면 결과가 자료 수집에 쏠린다.

## Phase 2 — 블라인드 병렬 생성

생성자는 `spawn_agent`로 띄운다. 반드시 지켜야 할 것:

- `fork_turns: "none"` — 대화 맥락을 상속시키지 않는다. 다른 생성자의 존재조차 모르게 한다.
- 메시지는 **자기완결적**이어야 한다. 브리프 전문을 메시지에 넣는다.
- 모델·추론강도 override는 `fork_turns: "none"`일 때만 적용된다.
- 동시 실행 슬롯은 보통 4개다. 생성자 3명이면 한 번에 띄우고 `wait_agent`로 수확한다.

각 생성자는 **성격이 아니라 최적화 목표**가 달라야 한다. 같은 브리프에 "좋은 아이디어를 내라"만 붙이면 비슷한 답 세 개가 나온다.

| 역할 | 최적화 목표 |
|---|---|
| `strategic-ideator` | 최대 효과와 장기 레버리지, 전제 재정의 |
| `evidence-ideator` | 실제 사용자·증거·기존 사례 정합성 |
| `operational-ideator` | 제약 안에서 실행 가능한 구조와 MVP |
| `contrarian-ideator` (선택) | 나머지가 암묵적으로 동의하는 틀린 전제 |

역할별 프롬프트 전문은 **references/agent-prompts.md**에 있다. 그대로 복사해 브리프와 함께 전달한다.

모델 배치는 **references/model-routing.md**를 따른다. 요약하면 핵심 생성·심사에는 상위 모델(Sol·Opus·Sonnet 계열)을, 중복 제거·형식 변환 같은 기계적 작업에는 경량 모델(Terra·Flash)을 쓴다.

## Phase 3 — Clusterer (메인 에이전트)

수확한 후보를 메인이 직접 정리한다. 경량 모델에 위임해도 되지만 판단은 메인이 소유한다.

- 표현만 다르고 실질이 같은 후보를 묶는다
- 묶을 때 **고유한 차이는 반드시 보존**한다. 뭉개면 심사가 의미를 잃는다
- 각 후보에 `C1`, `C2` … 익명 라벨을 붙인다
- **작성 모델명을 제거**한다. 이 표는 메인만 보관한다

라벨↔모델 매핑표는 최종 보고 전까지 심사자에게 노출하지 않는다.

## Phase 4 — 익명 쌍대 심사

심사자도 `fork_turns: "none"`으로 띄운다. 편향 통제 규칙:

1. 후보의 작성 모델명을 제거한다
2. **후보 순서를 심사자마다 다르게 섞는다**
3. 서로 다른 회사 모델이 각각 평가한다
4. 한 심사자의 판정으로 결정하지 않는다

"Claude가 GPT를 평가하면 자동으로 공정하다"는 성립하지 않는다. 교차 회사 + 익명화 + 독립 2인 + 명시적 기준을 **함께** 걸어야 한다.

심사 질문 형식과 토너먼트 진행 방식은 **references/judging.md**를 읽는다.

`judges`가 2이고 두 심사자의 승자가 갈리면 Phase 5에서 메인이 논거를 비교해 결정한다. 심사자를 추가로 늘려 다수결하지 않는다.

## Phase 5 — Lead Synthesizer (메인 에이전트)

메인이 최종안을 만든다. 승자를 그대로 채택하거나, 승자를 뼈대로 삼고 탈락안의 강점을 결합한다.

결합할 때는 출처를 추적한다. "실행 단계는 C2, 위험 관리는 C4에서 가져옴"처럼 남긴다. 논리적으로 충돌하는 요소를 억지로 붙이지 않는다.

심사 의견이 갈렸다면 **어느 논거를 왜 채택했는지** 명시한다.

## Phase 6 — 최종 검증 (deep 모드)

`depth: deep`이면 Synthesizer와 **다른 회사 모델**로 검증자를 띄운다. 검증자는 새 아이디어를 내지 않고 다음만 본다.

- 브리프의 평가기준을 실제로 만족하는가
- 근거 없이 단정한 부분, 과장된 기대효과
- 하드 제약 위반
- 빠진 실패 시나리오

검증 결과는 최종안에 반영하거나, 반영하지 않았다면 이유를 남긴다.

## Phase 7 — 보고

**assets/report-template.md** 형식으로 출력한다. 필수 구성:

- 최종 기획안
- 핵심 가정과 그것이 틀렸을 때의 영향
- 탈락안과 탈락 사유
- 심사 근거 요약 (라벨↔모델 매핑은 이 단계에서 공개)
- 다음 검증 단계

`output` 경로가 지정되면 파일로 저장하고, 대화에는 요약과 링크만 남긴다.

## 선택적 challenge 라운드

`challenge_rounds: 1`일 때만 실행한다. Phase 4와 5 사이에 넣는다.

```
독립안 생성 → 심사자가 약점 지적 → 각 생성자가 자기 안만 1회 보완 → 최종 심사
```

보완은 **자기 안에 대해서만** 시킨다. 다른 후보를 보여주면 그 시점에 수렴이 시작된다. 무제한 토론은 비용만 늘고 새 정보는 줄어든다.

## 실패 시 대처

- **서브에이전트 모델 override 거부** — `fork_turns`가 `"none"` 또는 정수 문자열인지 확인한다. 전체 히스토리 포크는 override를 받지 않는다.
- **모델 슬러그 없음** — `/mnt/c/Users/inkyunp/.codex/opencodex-catalog.json`에서 사용 가능한 슬러그를 확인하고 references/model-routing.md의 대체 순서를 따른다.
- **후보가 서로 너무 비슷함** — 브리프가 답을 이미 규정했을 가능성이 높다. 브리프에서 해법 힌트를 제거하고 재생성한다.
- **생성자 실패·타임아웃** — 남은 후보로 진행하고 보고서에 결손을 명시한다. 2개 미만이면 중단하고 사용자에게 알린다.
